# 用 feynman_research 跑科研工作流

## 一句话

`feynman_research` 把一件研究工作交给另一个代理去做：你告诉它「做什么类型的研究」和「输入是什么」，
它拉起外部的 `feynman` 命令行工具，跑完之后把报告文本和产物文件清单还给你。

它不是一个普通的小工具。一次调用会启动一个完整的研究代理，短则几十秒，长则几十分钟。

## 什么时候该用它

- 用户要查某个科学问题的文献，要一份带引用的综述。
- 用户要比较几篇论文的方法和结论。
- 用户要复现某篇论文的实验结果，或把论文方法整理成可执行的实验步骤。
- 用户要审查一份研究方案、论文手稿或论文配套代码。
- 用户要把一份很长的文档（论文、报告）整理成结构化笔记。
- 用户明确提到 feynman、deepresearch 这类科研工作流。

## 什么时候不该用它

- 问题不需要看文献，靠常识或现有代码就能回答。这属于普通对话，直接答。
- 用户只是想搜一下网页。用 `web_search`。
- 用户要的是把一次对话写成笔记。那用 `session_search` 之类的本地能力，不必绕远路。

## 十一个工作流

`workflow` 参数只能取下面这些值。括号里是这个工作流大致在做什么。

| workflow | 做什么 | 要不要 input |
| --- | --- | --- |
| `deepresearch` | 围绕一个题目做深度检索，产出带引用的一页纸报告 | 要，写题目 |
| `lit` | 给一个主题或一篇论文做文献综述 | 要 |
| `compare` | 比较若干篇论文的方法与结论 | 要，写清比较哪几篇 |
| `draft` | 把已有材料写成论文草稿 | 要 |
| `recipe` | 把论文的方法写成可执行的训练或实验步骤 | 要 |
| `replicate` | 复现一篇论文的结果 | 要 |
| `audit` | 审查一份研究产物的严谨性 | 要 |
| `autoresearch` | 自动跑一轮从选题到结论的研究 | 要 |
| `review` | 评审一份手稿或研究方案 | 要 |
| `summarize` | 把长文按窗口切分后分层摘要 | 要，给出文件或文本 |
| `log` | 读取历史会话记录，产出结构化笔记 | 不要 |

## 怎么调

```
feynman_research({
  workflow: "deepresearch",
  input: "2023 年以后关于小样本条件下的蛋白质结构预测有哪些新方法",
  cwd: "/绝对路径/到/你的研究目录",
})
```

必填两样：`workflow` 和 `cwd`。

## input 怎么写（最容易出错的地方）

Feynman 是另一个代理，它**看不到本次对话**。它只拿到你写的这一段 `input`。

所以：

- 不要写「上面那篇论文」「刚才提到的那个方法」，它不知道指哪个。
- 把必要的背景、限定条件、期望的产出形式都写进去。
- 一篇论文就给标题加作者或 arXiv 编号；一个题目就把范围写窄一点，越具体越好。

反例：`input: "帮我研究一下这个"`。
正例：`input: "研究 diffusion 模型在蛋白质侧链构象预测上的进展，重点看 2023 年以后的论文，输出一页纸，带引用"`。

## cwd 为什么必填

`cwd` 是 Feynman 的工作目录，它的笔记、报告、下载的论文都落在这里。
这个目录对**你**是有意义的，对 DSH 主进程没有意义，所以必须由你显式指定。

选目录的两条建议：

- 用绝对路径，别用 `.`。
- 给这次研究单独开一个目录，例如 `projects/<项目名>/`，这样产物清单一眼就能看清。

## 拿到结果之后

返回值里有这几样值得看：

- `ok`：是不是正常跑完。`false` 时看 `exitCode` 和 `timedOut`。
- `artifacts`：本次**新增或改动**过的文件，相对 `cwd` 的路径。报告通常就在这里。
- `stdout`：Feynman 自己的输出，里面是它的研究过程与结论。

跑完之后你应该做的是：读一遍 `artifacts` 里最像报告的那个文件，把结论转述给用户，
而不是把 `stdout` 原样倒给用户。用户要的是研究结论，不是另一个代理的日志。

## 两个已知的坑

- **超时**。默认上限是 30 分钟。`deepresearch`、`autoresearch` 这类有可能跑得更久，
  需要时在调用里传 `timeoutMs`。
- **不要并发跑**。这个工具被标成不适合并发，一次跑一个。连着调用多次会排队，慢上加慢。
